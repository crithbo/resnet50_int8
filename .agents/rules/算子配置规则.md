# 算子配置生成与验收规则

最后更新：2026-08-06（增加原生实例逐字段适用性、handler能力与组合边界门）

本文件只保存所有算子共有的配置生成、provenance 和证据门。读取范围由
`生成前必读索引.md` 决定；LC、MSE、Buffer、SA、GA、N2N 的固定公式和 RTL 反例移至
`NDP硬件字段语义.md`，按本轮实际触发的单元条件阅读。算子特有数值、layout、schedule
和动态门只写入专项规则。

## 1. 两种工作模式

### 1.1 复现模式

目标是精确复放已有授权配置。静态 JSON 必须有固定路径和来源身份；graph/tensor 缺少
原生专用入口时，只能使用用户授权、可审计且不改变配置语义的最小 bridge。地址、
mapping、bitstream、execplan 和 SCA/SCA_D 仍由锁定工具链重新生成。

### 1.2 开发模式

只有用户明确要求新算子、shape 或配置语义时启用。生成前必须同时具备：

- typed request、op type、输入/输出 dtype/shape/layout；
- qparam 或明确 `not-applicable`；
- 数值方程、舍入/饱和、padding/tail identity；
- stage DAG、slice/wave、buffer/stream/array schedule；
- 地址与跨 stage 生命周期；
- 授权模板/RTL/encoder/planner 的字段 provenance；
- 独立 golden 和专项发布门。

配置存在、模板正确或服务器自然结束都不能自动批准派生配置。

### 1.3 纯配置正确性绕行模式

规则 ID：`CDA-CONFIG-ONLY-CORRECTNESS-BYPASS-001`

当目标原生路径被反例否决、缺少精确变体或用户冻结功能 RTL 修改时，允许以多 stage、
显式 scratch、串行 occurrence、输入/常量重放、额外 barrier 或较低单元利用率构造
config-only correctness baseline。该模式只改变配置、调度和物化资产，不授权修改
`rtl/**`。

每个绕行合同必须显式记录：

```text
bypass_reason
contradicted_or_missing_native_path
exact_equivalence_scope
materialized_configuration_mechanism
performance_and_resource_cost
unresolved_production_blocker
claim_boundary
```

绕行放行至少要求：

1. 对完整合法输入域或冻结目标实例域证明数值顺序、舍入、饱和、padding/tail 和
   overflow/wrap 等价；
2. 最终 materialized JSON 反解后仍满足绕行不变量，不只验证生成器摘要；
3. mapping、bitstream、execplan/SCA、地址、lifetime、terminal 和 config-bound
   simulator 全部闭合；
4. 保留被否决原路径的 negative control，防止错误路径重新混入；
5. 明确吞吐、occurrence、scratch、traffic 和 barrier 代价。

满足上述门的资产只能称 `CONFIG_ONLY_CORRECTNESS_BASELINE`。没有独立性能证明和正式
动态闭环时，不得称 production/performance release；不得用“能跑通”降低数值或证据门。

规则 ID：`CDA-CONFIG-ONLY-INPUT-REPLAY-NONCOMPUTATIONAL-001`

输入/常量重放只允许复制原始 typed input、已经由正式 producer 计算并交付的 output，
以及冻结常量；重放不得改变 dtype、值域、数值阶段或计算所有权。除非另有独立批准的
算子分区合同明确拥有该计算并把新边界写入 typed graph，否则不得由 host 预计算
scaled、rounded、saturated、final output 或其他算子内部 tensor，再把它作为本算子的
config-only correctness baseline。任何 replay 合同必须列出源 producer、tensor identity、
允许的 index/address 映射和未跨越的计算边界。

### 1.4 复用优先整网集成模式

规则 ID：`CDA-REUSE-FIRST-DEFERRED-RETEST-001`

用户已明确授权：对 ndp-sim 中已有测试记录、用户授权参考、已经过本项目验收，或由主线
批准为等价复用的算子/原语，不再进行算子级复测，直接进入 ResNet50 整网集成；只有最终
集成的首个数值、地址、lifetime、terminal 或动态分歧命中该资产时，才重新打开对应
family 查验。

复用资产只需建立不可变的 integration binding，不重新执行其 operator golden、
定向 unittest、config-bound simulator、单算子 mapping 重建或动态运行。binding 至少记录：

```text
source path and immutable SHA
authority / prior evidence receipt
reuse class: EXACT_FULL_OPERATOR | APPROVED_EQUIVALENT | STRUCTURE_OR_PRIMITIVE_ONLY
target nodes / stages
parameter, shape and layout substitutions
known open blockers deferred to integration
fallback owner when first divergence is observed
```

执行边界：

1. `EXACT_FULL_OPERATOR` 与主线明确批准的 `APPROVED_EQUIVALENT` 可直接进入整网
   graph、allocator、execplan 和 simulator assembly；不因缺少本轮单算子复测而停止。
2. `STRUCTURE_OR_PRIMITIVE_ONLY` 只能覆盖其实际计算边界。输入 dtype、算术公式、
   rounding、saturation 或 output qdomain 不同的模板，不能被记为完整目标算子；缺失计算
   继续由共享 capability gap 拥有，但已相同的字段、拓扑和 transport 不再复测。
3. 整网 assembly 仍须检查 133-stage graph 拓扑、typed edge、全局地址、allocation、
   lifetime、CONFIG 继承、terminal 和最终产物可引用性；这些是集成一致性检查，不是算子
   算术复测。
4. 已知 blocker 在复用时标记为 `DEFERRED_TO_INTEGRATION`，不得伪记 close。没有集成
   分歧时不回到单算子；出现分歧时只重开首分歧 owner，不进行无差别全族回归。
5. 免复测资产的声明为 `REUSE_ACCEPTED_FOR_INTEGRATION`，不自动增加 E2、E4、E5、
   正式 target 或三方闭环计数。最终整网证据形成后再按公共证据等级升级。
6. 本模式不授权功能 RTL 修改、服务器文件检查、上传或运行；这些仍需用户单独授权。

## 2. 来源与身份

1. 活动/参考仓身份由 `repos.lock.json`、机器合同和本轮读取收据确定，不在本文件写死
   临时 commit。
2. 用户授权配置可用于精确复放和规则提炼。普通开发模式下，新 shape、地址、常量、
   拓扑和跨 stage 状态仍须独立验证；`CDA-REUSE-FIRST-DEFERRED-RETEST-001` 下只做
   integration binding 与整网一致性检查，不重复算子级验证。
3. 项目后加 JSON 不因位于 `ndp-sim/jsons` 或文件名相似而获得上游授权。
4. `ndp-sim-ref` 默认禁用；只有专项规则/机器合同明确给出 commit、文件、用途和 SHA
   时才能在隔离流程中使用。不得把例外扩展到未登记内容。
5. 原 JSON、冻结包和服务器原始回传永不原地修改。strict 副本、地址绑定副本和候选
   使用全新路径。
6. tensor/golden/初始化数据必须来自锁定原生脚本、正式 W3/模型或用户明确提供的独立
   输入。每份数据记录脚本、命令、shape、dtype、layout、bytes 和 SHA-256。

### 2.1 原生参考实例的逐字段适用性

规则 ID：`CDA-NATIVE-REFERENCE-FIELD-APPLICABILITY-001`

锁定 upstream commit 中、工作树内容与 pinned blob 一致且列入活动 authority 合同的
`ndp-sim/jsons`，其已有字段只对以下完整 source identity 构成正确实例：

```text
repository + commit + blob OID + file SHA
+ source op/dtype/shape/layout/qparams/topology/address/schedule
+ exact source consumer
```

这项权威证明 source instance 的字段值正确，不自动批准 target instance 的新 shape、
dtype、layout、qparam、地址、常量、拓扑、跨 stage 状态或 current consumer。项目新增、
untracked、工作树修改、只因路径位于 `ndp-sim/jsons` 或文件名相似的 JSON，不得声明
`REFERENCE_EXACT`。

新算子或新实例生成完整 JSON 前，必须对最终 candidate JSON 的每一个 leaf 建立唯一
`field_provenance_ledger`，至少记录：

```text
json_pointer / target_value
origin
source repository/commit/blob/path/file_sha/json_pointer/value
applicability_class
op/dtype/shape/layout/qparams/topology/address/schedule/consumer exactness axes
semantic owner
current consumer equation
derivation receipt
negative-control identity
status
```

`origin` 只允许：

```text
REFERENCE_EXACT
MODEL_DERIVED
RTL_DERIVED
ENCODER_DERIVED
ADDRESS_PLANNER_DERIVED
SCHEDULE_DERIVED
EXPLICIT_DISABLED
UNRESOLVED
```

适用性只允许 `EXACT_SOURCE_INSTANCE`、`PROVEN_INVARIANT`、
`DERIVED_FOR_TARGET`、`EXPLICITLY_INACTIVE`、`UNRESOLVED`。
`REFERENCE_EXACT + EXACT_SOURCE_INSTANCE` 要求上述 exactness axes 全部相等且 source
leaf 与 target leaf 值一致；某个 axis 不等但字段确为不变量时，必须改记
`PROVEN_INVARIANT`，绑定当前 consumer 方程、派生收据和能击穿错误外推的负控。

源实例没有某字段时，不得自动解释为零、默认值或 schema 错误。机器记录必须区分：

```text
SOURCE_ABSENT_NOT_APPLICABLE
SOURCE_ABSENT_UNKNOWN_FOR_TARGET
EXPLICIT_NULL_INACTIVE
EXPLICIT_ZERO
TARGET_REQUIRED_DERIVED
```

target strict JSON 的 required leaf 仍必须全部解析；补值优先级固定为 typed model request
→ current encoder schema → current RTL consumer equation → 已授权 address planner/
schedule。禁止 nearest-template、implicit-zero、从旧失败包/服务器残留补值，或由字段
同名推断 target value。

状态为 `COMPLETE` 的 candidate 不得含 `UNRESOLVED` 或
`SOURCE_ABSENT_UNKNOWN_FOR_TARGET`，其 ledger JSON-pointer 集必须与 strict candidate
的全部 leaf 一一相等。无法证明的字段应以 `BLOCKED` 和精确 leaf 集结束，不得通过生成
服务器测试包试错。共享机器入口为
`tools/validate_complete_operator_json_candidate.py`；它只裁决本地完整 JSON，不生成
mapping、bitstream、execplan、SCA 或服务器包。

### 2.2 原生 handler 的能力矩阵

规则 ID：`CDA-NATIVE-HANDLER-CAPABILITY-MATRIX-001`

存在原生 JSON、operator registry key、control-register handler 或生成命令成功，只证明
相应入口存在，不证明它支持 target instance 泛化。每个新算子族必须按实际 handler
source span 和 SHA 发布下列能力矩阵：

```text
exact_replay
shape
dtype
qparam
layout
address
cross_stage_schedule
```

每个能力必须有 current source/测试/消费者证据。handler 缺失、明示 placeholder、
example 或 conservative 时，默认只允许 exact replay，以及由 current planner/consumer
方程另行证明的地址 relocation；不得声明 shape、dtype、qparam、layout 或跨 stage
schedule 泛化。

generator 必须枚举静态模板中全部受 shape/dtype/qparam/layout/address/schedule 影响的
leaf，并与 handler 实际 update set 及最终 ledger 对照。target 发生变化的每个 axis，
所有 dependent leaf 都必须由具备该能力的 handler 或获授权的哈希绑定 patch覆盖；
遗漏、owner冲突、placeholder越权或 `UNCOVERED` 均 fail closed。批准工具补丁仍不等于
批准算子数值语义；field ledger、专项方程和独立负控继续适用。

### 2.3 原生 primitive 的组合边界

规则 ID：`CDA-NATIVE-COMPOSITION-BOUNDARY-001`

使用两个以上原生 primitive 构成一个 target operator，例如 `avgpool+quant`、
`add_dequant+requant` 或 `GEMM topology+INT8 accumulate`，不得因每个 primitive
分别存在或曾通过测试而批准 composite。每条 primitive 边界必须显式闭合：

```text
producer/consumer dtype
shape and layout
producer exact accepted byte-set
consumer required byte-set
transaction bytes
tag/last semantics
owner clock and qualified handshake
lifetime/write visibility
qparam/rounding/saturation
```

producer byte-set 与 consumer required byte-set 必须相等；仅总字节数相同不能掩盖
gap、overlap、row/bank/lane、transaction 或 multiplicity 错位。状态为 `COMPLETE`
时所有边界必须 `RESOLVED` 并绑定证据；任一边界未知时 candidate 固定为 `BLOCKED`。
primitive 的局部成功、Dequant 的 E4/E5、自然完成或另一算子族的数值结果均不能提升
composite，也不得替代目标 family 的正式动态门。

### 2.4 完整 JSON 与当前在测配置的静态对比

每个新 candidate 在结束本地 JSON 生成前，必须与本族 current 在测/待测资产实际消费的
最终配置逐 leaf 对比，并结合最新 package/return/task-record 将差异分为且只分为：

```text
SAME
INTENTIONAL_DERIVATION
SUSPECTED_CURRENT_DEFECT
NEW_CANDIDATE_DEFECT
DYNAMIC_ONLY
CURRENT_ABSENT
```

对比必须绑定 candidate/current 路径和 SHA、字段值、理由及证据，并单独把 current
blocker 分类为 `CONFIG_EXPLAINS`、`CONFIG_CONTRIBUTES`、`CONFIG_EXCLUDED`、
`DYNAMIC_ONLY` 或 `INSUFFICIENT_EVIDENCE`。observer/package/runner/RTL 或未到达目标
stage 的问题不得因配置有差异而强行归因 CONFIG；反之，已由 consumer 方程和历史反例
确定的配置错误不得降为动态未知。current 配置不存在时必须逐 leaf 标
`CURRENT_ABSENT`，不能拿其它 family 或最近似模板冒充 current baseline。

### 2.5 完整 JSON 的 family scope 必须绑定 lowering 与精确 stage 集

规则 ID：`CDA-COMPLETE-JSON-FAMILY-SET-SCOPE-FAMILY-OR-STAGE-PREDICATE-001`

全族 coverage 不得只按可跨逻辑算子复用的硬件 primitive 名选择。`RequantizeUint8`、
`DequantizeLinear` 等 `hw_op_type` 同时被多个逻辑算子族消费时，只用
`target_hw_op_types` 会把其它族的 stage 错纳入 expected set，造成伪 missing；反过来，
使用未绑定 lowering 身份的人工子集又会隐藏真实漏项。

fresh family-set manifest 必须提供：

```text
family_scope.mode = PINNED_EXACT_STAGE_IDS
family_scope.lowering_sha256 = 本轮实际 lowering bundle SHA-256
family_scope.expected_stage_ids = 本族全部逻辑 lowering stage 的非空唯一列表
```

validator 必须先验证 lowering SHA，再逐 ID 从该 lowering 读取真实 identity；
`target_hw_op_types` 此时只做逐 ID 的真实 `hw_op_type` 绑定，不再扩张 selector。它只登记
target lowering stage 的真实类型，不得因候选内部复用了 Conv/GEMM 等 source primitive
而加入 source 类型。

validator 必须报告 scope mode、绑定 lowering SHA、逐 stage identity receipt、完整
expected IDs、missing、duplicate 和 unexpected。缺少 expected stage、重复 stage、
stage 的真实类型不在 `target_hw_op_types`、额外跨族 stage、lowering SHA/ID 漂移均
fail closed。

在 v1 fresh manifest 迁移完成前，未含 `family_scope` 的既有 family-set 可保持原
`target_hw_op_types` 选择语义，但报告必须显式标为
`LEGACY_HW_OP_TYPE_SELECTOR`、`legacy_scope_compatibility=true` 和
`migration_recommended=true`；不得静默改变其 expected set 或旧结论。该兼容模式不得
用于新族或共享 primitive 的首次全族放行。

该 scope 只裁决全族静态 coverage，不提升 candidate 的 `COMPLETE/BLOCKED`、数值、
mapping、动态终止或正式 D。

## 3. JSON 与产物层级

必须区分：

1. `model_execplan/op_json/*.json`：复合图、参数、source、shape、slice mask；
2. `jsons/*.json`：硬件原子静态配置；
3. `*_withbaseaddr.json`：planner 写入实例地址/参数后的最终配置；
4. mapping、parsed/64b/128b bitstream；
5. `execplan.txt`、`cfg_pkg`、SCA/SCA_D、可选 `Bank_data`；
6. tensor/golden/relayout 和正式 readback。

第 3～6 层不得倒灌为第 1～2 层输入。最终文件不能从参考目录、旧失败包或服务器残留
补齐。

## 4. 语义所有权与物化回环

规则 ID：`CDA-CONFIG-SEMANTIC-OWNERSHIP-001`

每个最终 JSON leaf 必须有唯一 owner：

- typed request/model 参数；
- 算子数值或 layout 合同；
- logical ScheduleIR；
- 授权模板的精确不变量；
- planner/address binder；
- mapper/encoder 的物理放置。

owner 未知、多个 owner 冲突或值来自“沿用旧包”时 fail closed。`src_id`、loop、
stream、buffer、terminal、padding/tailing、CONFIG 和常量不得由 shape 猜测。

规则 ID：`CDA-CONFIG-MATERIALIZED-NONBASE-FIELD-OWNERSHIP-001`

生成器必须在编码前对受信任的静态/逻辑配置与最终 address-bound/materialized JSON 做
逐 leaf diff。物理 base/offset 等 planner 明确拥有的字段可按合同变化；任何 loop、
`dim_stride`、transaction、stream/Buffer/Array 连接、terminal、常量或其他非 base 字段
发生变化时，必须在本族机器合同中逐字段声明 owner、输入来源、变换公式、旧值、期望新值
和授权理由。缺少声明、实际 diff 超出 allowlist 或多个 owner 给出冲突值时，生成
fail closed。

覆盖证明必须从最终 materialized occurrence/address 方程重新计算每个正式输出 region 的
已写 byte 集合；静态 JSON 的覆盖、最终文件可编码或部分 readback 数值正确均不能替代该门。
本规则吸收并规范化
`HUMAN-JSON-MATERIALIZED-NONBASE-FIELD-OWNERSHIP-001` 提案。

规则 ID：`CDA-CONFIG-MATERIALIZED-ROUNDTRIP-001`

validator 必须针对最终 materialized/address-bound JSON，而不只针对公式模型或生成器
中间摘要。至少反解并验证：

- loop 数值域、trigger/tag/backpressure 图和 terminal；
- 每条 stream 的 transaction bytes、ordered occurrence 和 request address；
- memory 供给、Buffer AG spatial bank/byte 写入和 Array 消费数量守恒；
- producer/consumer、mask、ping-pong、lifetime 和 write visibility；
- typed output 覆盖、padding/tail、地址 region 和独立 golden；
- 最终 JSON→mapping→bitstream→execplan/SCA 的字段/位级一致性。

请求总数、schema valid 或本地公式正确不能替代上述回环。

规则 ID：`CDA-CONFIG-CAUSAL-TRANSACTION-LEDGER-001`

新算子首次物化，或本轮修改 transaction、loop、stream/buffer/array 连接、mask、
terminal、address、lifetime、CONFIG reuse/update、mapping 或 execplan 时，必须从最终
address-bound JSON、mapping/bitstream 解码和 execplan/SCA 生成统一
`causal_transaction_ledger`。它只覆盖 changed causal slice，不重复计算 byte-identical
numeric/W3/golden 或无关 stage。

每条 enabled `producer→Buffer→consumer` 边至少记录：

```text
producer ordered occurrence/multiplicity
producer transaction bytes and exact byte-set/hash
Buffer row/bank/lane/strobe valid-set
consumer request occurrence/mask/required byte-set
accepted terminal index domain and release threshold/classification
ping-pong/keep/full notification carrier
queue/capacity maximum occupancy bound
lifetime acquire/release and write-visibility boundary
formal D region/line coverage when applicable
```

静态放行必须满足：

1. producer 的 exact byte-set 与 consumer required byte-set 相等；协议声明的重复读取须有
   独立 multiplicity 合同，不能用总字节数相同掩盖 gap、overlap、bank/lane/row 错位；
2. 每个必需 terminal occurrence 都必须被最终 threshold 分类为 release，而非 ignore；
   terminal carrier、ping-pong/keep/full threshold 与直接 consumer 的 last/last_index
   必须闭合；
3. 按 execplan 顺序计算的最大 queue/Buffer 占用不得超过容量，读写及 CONFIG
   reconfigure/reuse 不得在 lifetime acquire 前或 release 后消费；
4. 地址覆盖、写可见性和正式 D region 必须来自同一 ledger，禁止分别使用互不绑定的
   “地址通过”“请求数通过”“D 文件数通过”摘要；
5. ledger 必须绑定 final config/mapping/bitstream/execplan/SCA SHA、生成器版本、完整
   枚举数、ordered hash、边界样本及 claim boundary。仅最终 ZIP 引用该物化配置时，
   服务器包 `release_gate_matrix.materialized_config` 才消费该收据。

负控按适用失败机制合并，每类只保留一个真实变异：删除/重复一个 producer window、
翻转一个 required mask bit、把 terminal threshold 改为相邻错误值、偏移一个 transaction
地址、缩短一个 lifetime/release。不得为增加负控数量枚举所有同义 token/字段；最近同类
服务器反例必须保留。exact config 与 causal slice 未变时可复用 byte-equality/current
receipt，不重复生成全量 ledger。

规则 ID：`CDA-CONFIG-BOUNDARY-MICROTRACE-001`

上述 ledger 中任何 changed terminal、threshold、mask、ping-pong、keep、buffer-valid、
queue capacity、lifetime 或 CONFIG reuse/update 判据，都必须使用活动 RTL/encoder 已绑定
方程运行本地 metadata-only 边界微轨迹。该门不运行 DUT 数据通路、不执行完整仿真，也不
重算 tensor 数值；只运行最终配置实际会触发的控制判据。

每个 changed 判据至少覆盖：

1. first、penultimate、intended final 和 one-after-final occurrence；
2. threshold 的 `index<T`、`index==T`、`index>T`，并按实际 signed/unsigned/位宽 wrap
   方程裁决 ignore/matched/out/release；
3. producer window 的首/末 byte、相邻 window 接缝、required mask 的每个 active
   bank/lane，以及缺一 window、重复 window、gap、overlap；
4. queue empty→nonempty、capacity-1→full、同周期 push+pop，以及 lifetime
   acquire/use/release 前中后；
5. stage/config 边界上的 disable/update/reuse 和 ping-pong/keep 切换。

若控制方程依赖本地无法可靠建模的跨时钟动态状态，机器记录必须标为
`DYNAMIC_ONLY_BOUNDARY`并列出最小服务器 observer；不得伪造本地 PASS，也不得因此把
完整 DUT 仿真搬成本地阻断门。若存在历史服务器反例，必须保存最小旧配置 trace：旧配置
重现失败、新配置通过。微轨迹与 ledger 应由共享核心或专项 extension调用，不得复制整套
服务器 final-ZIP/runner/return 自检。

冻结实证：

- Conv node0004 的 accepted terminal index 为4/5，旧
  `transout_last_index=2`使256/256 occurrence进入 ignore；按相同5-bit RTL方程改为5后
  256/256 release；
- QLinearAdd node0007 split-C 的每侧 producer 只给一笔16B，而ARM要求完整32B row；
  `[0,16) ∪ [16,32)=[0,32)`才满足 exact byte-set，删除、重复、gap、overlap或缩窄mask
  均必须 fail closed。

规则 ID：`CDA-CONFIG-PHYSICAL-BANK-ROW-VALIDITY-001`

新算子首次物化，或本轮改变任一 preload、input/output、CONFIG、execplan、scratch、D
region 的地址、长度、transaction、stride 或映射时，不能只验证“地址小于总容量”或
“逻辑区间不重叠”。发布前必须按服务器将实际编译的云端权威 RTL、参数和 encoder
公式，对最终 materialized 地址区间逐项解码为 bank/row/column/byte-lane，并证明其物理
可达。

每个 changed final interval 至少记录并验证：

1. source owner、direct consumer、base、length、transaction、alignment、slice/local/global
   地址域及 final config/mapping/bitstream/execplan/SCA SHA；
2. first line、final line、每个 bank 切换点、每个 row 边界和跨边界前后各一行的
   bank/row/column 解码；区间较小时必须完整枚举；
3. bank enable、row 合法集合或空洞、column/line 对齐、位宽截断/wrap、跨 bank/row
   连续性，以及区间间 overlap/alias；
4. SCA preload、ExecutionPlan base、runtime preflight、readback/return target 等所有
   direct consumers 使用同一个已验证的最终地址，不得只更新其中一个副本；
5. 若云端 RTL 仅改变 queue/handshake 而地址位宽和 decode 方程未变，可复用已绑定的
   decode receipt；若 decode、bank enable、row 大小或地址位宽改变，则必须重跑本门，
   不能用本地旧 RTL 收据替代。

最低负控必须包含：

- 地址在 aggregate 容量内但解码到 disabled bank 或非法/空洞 row；
- 跨 bank/row 边界的 one-line off-by-one、位宽 wrap 或错误 alignment；
- 只更新 SCA/manifest 而保留旧 ExecutionPlan base 或 runtime guard 的 stale consumer。

任一负控未 fail closed、任一 direct consumer 未覆盖、任一 interval 出现非法物理行或
未知 decode provenance 时，不得生成 `PACKAGE_READY_NOT_RUN`。该门只执行地址/metadata
解码和少量边界枚举，不运行完整 DUT 仿真、不重算 numeric/W3/golden；未改变且逐字节
相同的地址区间可按 current byte-equality receipt 复用。

冻结反例：node0071→node0075 v5 的首条 SCA preload 地址 `0x01706400` 虽未超过约定的
aggregate 24MiB，却解码到 bank2、row `0x1c19`，命中禁用 bank/非法 row，导致 CONFIG
和 stage00 之前518/518 readback为X。v9将D、32个CONFIG和ExecutionPlan整体迁移到已枚举
通过的低 bank-row 区间，并同时更新全部 direct consumers；该反例必须保留为本规则的
aggregate-in-range-but-physically-invalid 负控。

这些收据只证明配置控制边界和物化守恒，不替代真实 compile、natural terminal、正式 D
或 E4/E5。

## 5. strict JSON 与 CONFIG

1. 配置必须通过严格 schema。未知/缺失字段、错误数组长度、非法 enum/null、地址
   fallback、位宽截断、非正向批准 loop 均失败。
2. legacy JSON 不改写。只允许由受控 materializer 在源 SHA、精确 diff 和编码等价门
   下生成 strict 副本。
3. write stream 的 read-only 字段、typed-null sentinel 等 legacy 清理必须有
   encoder/RTL 等价证明；padding value 还必须有算子 padding contract。
4. `CONFIG` 按 IGA/LSU/SA/GA 的 enable/update 位解释为跨 stage 持久状态。
   首 stage reuse、disable+update、reuse 时 body 漂移、disable 后无状态 reuse 均失败。
5. 每个 stage 分别记录：

   ```text
   json_emitter_ready
   rtl_semantics_compatible
   dynamic_release_ready
   ```

   candidate JSON 要求前两项为真；正式发布还要求第三项和 E4/E5。

## 6. 数值、qparam、layout 和 stage DAG

1. 每个 operator 哈希绑定 op type、输入/输出 dtype/shape/layout、stage role/dependency、
   qparam、padding/tail 和 source provenance。
2. qparam 可为标量或 per-channel tensor descriptor。per-channel 必须记录
   `value_kind`、dtype、shape、element_count、axis、min/max、`value_sha256`；禁止退化
   为首元素标量。
3. B′ 等独立输入必须有独立 producer/SCA；不得把 B 别名为 B′。
4. 每个整数除法/分片必须证明整除或显式 padding/tailing；禁止静默截断。
5. 跨 stage 必须证明 CONFIG、buffer/stream state、scratch write/read 可见性和终止
   顺序。独立单 stage 包不能冒充零拷贝串联。
6. 数值路径必须按目标实现的精确操作顺序和舍入点比较；代数等价不能替代逐 bit 等价。

## 7. mapping、bitstream 与 execplan

规则 ID：`CDA-CONFIG-FULL-REBUILD-PROVENANCE-001`

配置语义、地址或 mapping 变化后，以本轮最终 address-bound JSON 为唯一输入完整重建：

```text
planner → encoder → mapping → bitstream → execplan → SCA/SCA_D
```

具体门：

1. placement 必须 exact penalty=0、`fallback_used=false`，记录 cache 初态、seed、命令、
   工具 commit/tree、stdout/stderr 和输出哈希。
2. cache 默认为空。唯一可用历史 cache 必须来自锁定提交、保持原生 key，由当前 mapper
   对当前图重新计算 exact penalty=0；只看到 load 日志不构成证据。
3. source JSON、mapping review、parsed bitstream、64b/128b dump 必须由独立镜像逐字段/
   逐 bit 一致；silent default 或 wrap 均失败。
4. mapping 必须针对最终 base/address-bound JSON。address-unbound mapping 只能作预检，
   不能与 address-bound execplan 拼接。
5. 每个 graph operator 唯一绑定 patched JSON、mapping evidence、cfg_pkg 和
   Load_Config。
6. 独立解析 128-bit execplan；机器位与 explanation 的序号、opcode、slice、register、
   value、operator 一致，重复序号失败。
7. 按真实 `Load_Config→Write_Reg→Start_Comp` 顺序回放 CONFIG/地址状态，不能只看单份
   JSON 或 explanation。
8. 至少两个隔离工具副本重跑；除登记的非确定可视化文件外，下游产物逐文件哈希一致。
9. 每个产物保存本轮路径、bytes、SHA-256 和命令收据。哈希偶然与旧版相同不能代替
   provenance。

规则 ID：`CDA-EXECPLAN-BARRIER-OPCODE-LIVE-DRAIN-SEMANTICS-001`

跨 stage 或跨 operator 的 barrier 只有同时满足以下条件才可计入配置、execplan、lifetime
或服务器包的生产者可见性闭环：

1. current active RTL 必须把目标 opcode/field 解码为 live control state transition；
   只在常量、注释、说明、execplan machine word 或 explanation 中出现不成立；
2. barrier release 必须在目标 visibility domain 证明 producer writes 全部 accepted，
   且相关 FIFO/queue drained、outstanding=`0`，或提供形式等价的有序可见性证明；
3. `Start_Comp` 串行、finish、last-data ingress acceptance、配置命令存在、observer
   snapshot 或 host 顺序均不能替代上述 release 语义；
4. 生成前本地 validator 必须把“opcode 未 live decode”“状态机/transition 缺失”
   “release 未绑定 drain/outstanding/visibility”作为独立负控 fail closed。该门只验证
   能否安全上服务器，不要求在服务器侧重复环境自检。

冻结反例：e1fb0f7 的 node0071→node0075 联合链中，execplan 虽含 opcode `3'b110`，
`Slice_Execution_Manager.sv` 仅声明 `BARR_CMD_OP`，没有 barrier valid decode、FSM 或
visibility release；IDLE 可把该命令作为 no-op 消费。该命令不得关闭 producer→consumer
可见性 blocker。

## 8. 地址、transaction 和覆盖

通用地址方程及各单元 bit 语义见 `NDP硬件字段语义.md`。所有算子共同要求：

1. base/transaction 按实际 RTL 位宽和顺序计算；不得把 `idx_size` 当 loop range。
2. 每 slice 的真实 base 必须回放 execplan Write_Reg，不能由 slice0 JSON 外推。
3. 全部请求和 SCA region 满足对齐、bank/column/row、位宽 wrap、region、overlap/alias
   和生命周期合同。
4. padding/tailing 不抑制 memory request；read 是值替换，write tail 是
   read-modify-write merge。
5. 大规模报告可压缩行，但必须完整枚举，保存 multiplicity、unique count、ordered hash
   和边界样本；禁止抽样放行。
6. typed output 字节数、不同 transaction base 数、正式 readback line 数必须守恒。
7. 多 read/write 分支共享 LC root 时必须提供 backpressure 无环和进度证明；否则采用
   授权模板的独立 branch roots。

## 9. 原生 pipeline 与项目补丁

对 native 已支持 op type，必须生成/适配原生 op_json 并调用活动
`model_execplan/main.py`。直接复用其：

- graph/source/shape parser；
- control-register handler；
- output writer；
- address planner、mapping/bitstream、execplan 和 SCA pipeline。

项目 crosswalk/contract 只做索引、typed lowering、provenance、审计和放行判断，不得
实现第二套 graph parser、字段 patcher、地址规划器或 execplan generator。

native 缺少目标 handler 时，只有用户批准的哈希绑定 patchset 才能在隔离副本扩展原生
registry。活动 checkout 保持只读；base commit、source SHA、patch identity 任一不匹配
即停止。工具补丁被批准不等于算子语义被批准。

## 10. 证据等级和声明边界

证据等级及回归分类只采用 `.agents/rules/生成前必读索引.md` 的公共定义。对配置链，
结构 valid、内部 write、本地 mismatch=0 或未反解最终物化 JSON 均不能提高证据等级；
`formal_target_instance_allowed=false`、任一 unresolved blocker 或缺专项动态门时，
不得输出正式 target config。

`REUSE_ACCEPTED_FOR_INTEGRATION` 是调度/装配状态，不是 E0～E5 的新等级。它允许跳过
重复的算子级测试，但不会把历史参考、近似模板或未闭 blocker 自动升级为正式证据。

## 13. 停止条件

出现任一情况立即停止：

- typed/model/qparam/layout/schedule/地址/生命周期来源不完整；
- 必须从旧失败包、服务器残留、禁用来源或参考最终产物提取内容；
- 需要未授权修改活动源码或功能 RTL；
- strict JSON、mapping、bitstream、execplan、SCA、地址、物化回环或专项语义任一失败；
- 重复生成不确定、SCA 引用缺失或日志报告 silent failure；
- 试图用模板授权、本地 E2、自然完成或其他算子结果解除本算子 blocker。复用优先模式
  可以把 blocker 标记为 `DEFERRED_TO_INTEGRATION` 后继续装配，但不得把它写成 closed
  或正式通过。

停止时记录第一处差异、输入/工具身份、命令、日志、规则 ID 和最小 next action；不得继续
补文件或通过服务器试跑猜配置。
