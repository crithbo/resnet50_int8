# 如何用 AI Agent 推进复杂工程项目

这份教程主要想讲一件事：当我们接手一个规模较大、链路较长、需要持续迭代的工程项目时，应该怎样合理地使用 AI，与 Agent 建立稳定的协作方式，并通过规则文件、主线—分支体系、上下文管理和人工干预，让项目逐步向前推进。

这里讨论的重点并不是怎样写一句“更厉害的提示词”，而是怎样建立一套长期可用的工作方法。AI 的能力当然重要，但对于复杂项目来说，决定最终效果的往往不只是模型本身，还包括我们怎样组织信息、怎样拆分任务、怎样验证结果，以及怎样把每次成功或失败的经验保留下来。

## 一、先理解 Agent 是什么

普通的 AI 会话，主要是在回答当前问题。你提出一个问题，它给出解释、建议或者代码，然后由人决定接下来怎样执行。会话中的状态主要保留在聊天记录里，如果换一个会话、换一个账号，或者聊天内容经过多次压缩，之前积累的信息就可能逐渐丢失。

Agent 可以看成是在普通会话能力之上，增加了目标、工具、工作空间和执行反馈。它不只是回答“应该怎样做”，还可以直接读取项目文件、修改代码、运行命令、观察结果，再根据真实反馈决定下一步。

所以，相比普通会话，Agent 的优势不是每一次回答都一定更聪明，而是它可以围绕一个目标持续工作，把分析、执行和验证连接起来。对于工程项目来说，这种能力尤其重要，因为很多问题并不能只靠解释解决。一个方案是否正确，最终还是要看代码能不能运行、配置能不能被真实消费者读取、测试能不能通过、服务器能不能正常返回，以及输出是否符合预期。

但是，Agent 也有一些无法突破的限制。理解这些限制，是建立协作体系的前提。

首先，单个对话的上下文是有限的。一个复杂项目可能包含大量源码、配置文件、历史记录、测试结果和外部依赖，这些内容不可能始终完整地保存在一个对话中。当上下文逐渐填满以后，系统通常会压缩前面的内容。

压缩可以让对话继续进行，但它不是无损存档。第一次压缩可能只是省略了一些细节，多次压缩以后，Agent 可能逐渐忘记某个决定为什么做出、某条规则来自哪次错误，甚至忘记当前任务最初要解决什么问题。

其次，AI 的输出存在随机性。面对同一个问题，不同时间、不同会话，甚至同一个 Agent 的不同尝试，都可能给出质量不同的方案。对于简单任务，这种随机性通常影响不大；但对于某些复杂任务，只要其中一个步骤出错，整条链路就可能无法运行。

例如，一个任务可能同时涉及数据格式、地址规划、配置编码、测试包生成、服务器命令和结果回读。即使每个环节单独看起来都“基本正确”，组合在一起也可能因为一处细小错误而失败。有些问题连续尝试很多次仍然无法成功，不一定代表 AI 完全做不到，也可能是它缺少关键上下文，或者我们让它沿着一条本身就不合理的路线不断迭代。

因此，我们不能把“Agent 会一直记得全部信息”“它会自动发现计划错误”或者“复杂任务应该一次成功”当作系统前提。更合理的做法，是在 Agent 外部建立一套可以管理目标、状态、规则和经验的工程体系。

## 二、从零开始接手项目，先建立项目地图

接手一个陌生项目时，第一步不是立刻让 Agent 修改代码，而是让它先通读项目已有内容，对项目形成一个整体认识。

这一阶段可以让 Agent 查看项目目录、入口文件、主要模块、测试、配置、生成产物和已有文档，并回答几个基本问题：

第一，这个项目最终要完成什么任务，核心目标是什么？

第二，项目目前包含哪些主要模块，各自负责什么？

第三，哪些部分已经完成，哪些部分仍然缺失，哪些路线已经被证明不可行或者暂时冻结？

第四，项目最终用什么证据判断成功？是代码能够编译，测试能够通过，还是需要服务器真实运行并对输出进行比较？

Agent 通读以后，最好先给出一份项目地图，而不是直接给出修改方案。这份项目地图不需要特别长，但应该至少包含核心目标、主要目录及其职责、当前完成状态、关键依赖、明显风险和仍然无法确认的部分。

这一步非常重要，因为复杂项目中最常见的问题之一，就是把中间产物误认为最终目标。例如，生成了一份格式正确的 JSON，并不代表这份 JSON 对应的硬件行为正确；本地模拟能够运行，也不一定代表服务器上的 RTL 能够得到一致结果。

人需要重点确认 Agent 提炼出的核心目标是否准确。核心目标一旦理解错误，后续工作越快，偏离得越远。如果 Agent 对某个模块的作用还不确定，应当把它标记为未知项，继续阅读真实调用路径和下游消费者，而不是凭文件名猜测。

## 三、建立规则文件体系

当 Agent 对项目有了初步认识以后，下一步是建立规则文件体系。

首先是项目的基础规则文件，例如 `AGENT.md`、`AGENTS.md`，或者项目约定的其他稳定入口文件。这个文件会被新的任务或会话优先读取，因此它应该保存整个项目中最稳定、最重要的信息。

基础规则文件可以包含以下内容：

- 项目的核心目标和最终完成口径；
- 当前整体完成到什么程度；
- 主要模块、关键目录和重要资产分别在哪里；
- 不同类型的信息应该去哪个文件中查找；
- 主线和分支怎样协作；
- 项目有哪些不能越过的权限边界；
- 工作中需要始终遵守的整体规则。

但是，基础规则文件必须保持精简。它不应该保存某个版本的完整日志，也不应该记录已经结束任务的每一步操作，更不适合塞入某个分支才需要的全部字段细节。

如果基础规则文件不断增长，每个新任务都要读取大量与自己无关的信息，不但浪费上下文，还容易让规则互相污染。更好的方式是让基础规则文件只承担“稳定入口”和“信息索引”的作用：告诉 Agent 当前项目要做什么，以及需要进一步到哪里读取详细信息。

基础规则文件之外，还需要计划文件。计划文件只记录项目当前状态和短期计划，包括当前正在处理的任务、优先级、尚未解除的阻塞、下一步顺序和停止条件。

计划文件不应该承担完整历史记录的职责。已经完成的工作应当及时从活动计划中移出，否则计划会越来越长，旧的“下一步”和新的“下一步”混在一起，Agent 很难判断哪一条仍然有效。

接下来是历史文件和任务记录。历史文件用于保存项目执行过哪些操作、出现过哪些错误、哪些路线已经被证明无效，以及重要结论是怎样得到的。这样以后再次出现类似问题时，可以追溯到原始原因，而不是从头猜测。

历史记录也不需要无限堆积完整日志。比较合理的方式，是保留任务身份、关键步骤、最终结果、最早错误位置、相关证据地址和由此得到的结论。特别大的原始日志可以单独保存，历史文件只保留摘要和索引。

最后，每个分支任务都应该有自己的专项规则文件。专项规则只保存这个分支真正需要的内容，例如某一类算子的字段语义、已知反例、生成要求、验证方式、允许修改的范围和必须停止的条件。

一个分支不需要通读其他所有分支的规则。它只需要读取基础入口、当前任务单、相关公共规则和自己的专项规则。这样可以减少无关信息进入上下文，避免不同算子、不同实验和不同版本之间互相污染。

这套规则文件体系主要有三个优点。

第一个优点是方便任务转接。项目的关键知识保存在仓库中，而不是只保存在某个账号或某段对话里。即使更换 Agent、任务或者设备，只要重新读取规则、计划和历史，就可以恢复大部分工作状态。

不过，规则文件最好同时通过 Git 做版本管理，并在 GitHub 或其他远端保存备份。这样既能查看修改历史，也能降低误删、本地损坏或者 AI 错误操作造成的风险。

第二个优点是更好地管理上下文。对话压缩以后，不需要要求 Agent 凭记忆恢复全部内容，只需要让它重新读取基础规则、计划中的相关部分和当前分支规则。不同分支只加载自己需要的信息，可以减少上下文污染和性能损失。

第三个优点是降低随机性。每次成功完成任务以后，可以把有效方法提炼为规则；每次失败以后，可以把错误原因、反例和新的检查项写入规则文件。如果某个错误能够通过代码校验发现，还可以进一步把它写进测试、validator 或生成门。

这样，项目不是每次都从零开始碰运气，而是在不断积累经验。Agent 可能仍然会犯错，但同一种错误重复出现的概率会逐渐降低。

## 四、建立主线—分支体系

规则体系建立以后，可以进一步建立主线—分支的协作方式。

主线主要负责项目的控制面。它与人保持交互，维护项目整体目标、当前计划、公共规则、全局阻塞和整体进度，并向不同分支分发任务。

主线最好不要承担大量具体执行工作。这样做的好处是，主线的上下文不会被某个算子的调试细节、某次服务器日志或某个临时实现方案占满。人可以随时通过主线了解项目进展、调整优先级、讨论下一步方向，而不需要打断某条正在执行的工作。

分支负责具体任务的执行面。可以按照算子族、模块或者明确的专项问题建立分支，而不是为每一个很小的文件都单独建立一个会话。

例如，一个分支可以负责某一类算子的配置生成、mapping、bitstream、测试包和回传分析；另一个分支可以负责服务器测试基础设施；还有一个分支可以只消费用户提供的人工 JSON，并确保不会擅自修改输入。

主线向分支分发任务时，最好提供一份相对固定的任务单。任务单至少应该写清楚：

- 本轮要解决什么问题；
- 冻结使用哪些输入、版本和规则文件；
- 允许修改哪些路径；
- 用什么结果判断通过；
- 如果失败，怎样区分配置、RTL、观测器或测试包问题；
- 遇到什么情况必须停止并回报主线；
- 是否允许上传、运行服务器、修改外部系统或进行其他有副作用的操作。

分支完成任务以后，不只是回复一句“已经完成”，而应该结构化回传结果。回传中应包含本轮做了什么、实际得到什么证据、最后可信边界在哪里、当前阻塞是否发生变化、是否建议修改规则，以及如果需要下一轮测试，下一轮应该验证什么。

主线根据这些结果更新整体计划和规则文件，再决定下一步分发什么任务。

主线—分支体系的第一个优点是并行度更高，速度更快。多个互相独立的任务可以同时推进，不必等待一个会话逐个完成。

但需要注意，并行不会凭空增加整体能力。总工作量通常不会因为多开几个分支而消失，反而会增加任务分发、上下文准备、结果回传和规则同步的通信成本。因此，只有依赖清晰、资产隔离、验收标准明确的任务适合并行。

第二个优点是每个分支只读取自己的规则文件，减少上下文污染。一个分支专门处理一个问题时，它的上下文中会保留更多相关细节，单独处理能力通常会更强。

第三个优点是主线可以始终保持可交互状态。人需要了解项目进展、分析整体方向或者临时调整计划时，不必打断正在执行的分支。主线可以根据各分支的回传快速给出全局状态。

如果分支之间共享服务器、GPU、目录或者其他物理资源，还需要在主线中管理资源占用。同一个服务器根目录、同一份输出路径或者同一套临时文件不能被两个分支同时修改。逻辑上的并行不能破坏物理资源和证据身份的隔离。

## 五、先计划后执行

AI 在完成任务时，不一定真正理解人需要什么。它可能理解了表面目标，却没有理解最终验收方式；也可能在缺少关键信息时，根据已有经验补出一个看起来合理但并不适合当前项目的方案。

因此，在执行操作之前，应当先让 Agent 分析计划，或者把人的计划交给它复述。让它说明准备怎样做、依赖哪些假设、会修改哪些内容、用什么方式验证，以及遇到什么情况会停止。

如果有不懂的地方，Agent 应当及时提问。分支遇到阻塞时，也应把问题提交到主线，而不是自行扩大任务范围。

先计划后执行有两个直接好处。

一方面，人可以在真正修改代码、生成大量产物或者运行昂贵测试之前，提前发现理解偏差。另一方面，人可以掌握 Agent 正在沿哪条路线推进，避免它长时间闷头尝试，最后才发现方向并不是自己想要的。

但这里还要特别注意：分支或者主线通常没有很强的全局自我纠正能力。它可能会发现某个具体命令失败，却不一定会主动判断整个计划不合理或者代价过大。

只要当前路线还有可以尝试的动作，Agent 往往会通过更换实现、增加检查、修改参数或者扩大搜索范围继续前进。如果确实无法继续，它可能会报告阻塞，但不一定会主动提出完全换一个方向。

所以，人需要大致了解项目的前进方向。当一个任务长期阻塞时，可以观察几个信号：

- 多轮尝试以后没有增加新的证据；
- 测试范围没有缩小，代价却持续上升；
- Agent 只是在同一路线中反复更换实现细节；
- 当前测试无法区分几个候选原因；
- 每次失败都发生在不同位置，说明基础假设可能没有冻结。

出现这些情况时，人应该主动介入，重新定义问题、补充系统知识、改变验证顺序，或者暂时停止这条路线。

AI 给出的方向有时并不合理。这时可以试着从人的思路重新起步。

以本项目为例，一开始尝试让 AI 直接从 ONNX 文件出发，理解算子的计算步骤，再参考已有算子 JSON 学习写新的 JSON，然后直接上机测试。

这个思路表面上是连贯的：已经有一批参考 JSON，AI 也能理解算子公式，那么它似乎应该可以通过模仿生成新的算子配置。

但实际迭代多次以后效果并不好。原因在于，算子 JSON 并不是纯粹的数学表达。很多字段对应具体硬件单元、数据布局、地址生命周期、握手关系和控制时序。AI 只看到了输入 JSON 和算子公式，却不了解这些字段最终怎样被硬件消费。

也就是说，它学会了文件“长什么样”，却没有真正理解这个文件为什么这样写，以及某个字段改变以后会在 bitstream、执行计划和 RTL 中产生什么行为。

后来，我从人的角度重新分析，认为需要补齐 JSON 后面的消费链。因此，我给 Agent 增加了几类信息：

- 现有算子 JSON 对应的真实计算步骤；
- JSON 怎样被 mapper 和 encoder 消费并生成 bitstream；
- bitstream、execplan 和相关控制配置怎样驱动硬件运行；
- RTL 代码怎样读取这些字段，怎样完成地址、握手、计算和回读。

在补齐这些信息以后，再让 Agent 学习并生成规则文件，它对配置字段的理解明显更完整。它不再只根据格式仿写 JSON，而是能够沿着计算步骤、字段语义、bitstream、执行计划和 RTL 消费者逐层检查。

在此基础上继续迭代，大约五轮以后，Agent 最终写出了能够完成验证的 Dequant 算子配置，并在过程中独立发现了几个 RTL 问题。

这个案例说明，AI 的效果不理想时，不一定只是模型能力不足，也可能是我们没有提供它真正需要的系统知识。增加更多无关文档未必有用，关键是补齐从输入到真实行为之间缺失的因果链。

## 六、通过硬约束减少随机性

我们当然希望 AI 每次都给出更好的答案，而不是随机得到一个较差的方案。但完全消除随机性并不现实，更可行的方法是通过约束，把它能够选择的错误方向逐步排除。

从约束强度来看，通常可以分为三层：

代码硬约束强于规则文件约束，规则文件约束又强于用户口头约束。

用户口头约束适合表达本轮意图和临时要求，但最容易在多次压缩以后被遗忘。如果某条要求非常关键，只在对话里说一次是不够的。

规则文件比口头约束稳定。它可以被新的会话重新读取，也可以通过 Git 追踪修改历史。但是，Agent 仍然可能漏读、误读，或者在执行过程中没有严格遵照。

代码硬约束最可靠。如果违反要求就会导致 validator、测试、schema、preflight 或生成门直接失败，那么 Agent 不需要“记得”这条规则，也无法轻易绕过它。

因此，比较理想的方式是把规则文件和代码硬约束结合起来。

例如，生成测试包之前，要求 Agent 必须通读对应规则，并在包中加入规则读取收据，记录读取了哪些文件、对应的版本或哈希是什么。

包生成完成以后，再对最终包做一次独立自检。如果规则已经变化、收据缺失、输入身份不一致，或者某个必要文件没有进入包中，校验就直接失败，这个包不能交给主线。

主线不需要重新分析分支的全部过程，只要先检查这些硬门是否通过。如果没有通过，就直接打回。

每次成功执行任务以后，也可以继续问：这次成功依赖了哪些关键条件？其中哪些条件应该进入规则，哪些应该进入自动测试？

每次失败以后，同样可以问：这是一次偶然错误，还是可以推广为长期检查项？如果同类错误以后可以被程序自动发现，就尽量把它写成 validator 或测试，而不是只写一句提醒。

通过这种方式，成功和失败都会变成项目资产。规则体系会越来越准确，自动检查会越来越完整，Agent 的可选错误路径会越来越少。

## 七、把 AI 当作会犯错、但可以积累经验的协作者

目前 AI 的能力已经在很多领域得到证明，尤其是在数学推理、代码生成、资料整理和复杂模式分析方面。但它和人一样会犯错，也可能因为信息不足、上下文污染或者方向错误，连续给出不理想的结果。

如果发现效果不好，不妨先尝试调整使用 Agent 的方法，而不是只重复同一句要求。

可以把目标写得更明确，把完成口径变得可验证；可以补充真实消费者和执行链知识；可以把任务拆成多个分支，从不同方向尝试；也可以更换模型或者 Agent，让不同执行者独立给出方案。

但是，多分支和多模型不应该变成无组织地重复碰运气。所有尝试都应该回到同一套项目目标、规则文件和证据体系中。否则，即使偶然得到一个可以运行的结果，也很难判断它为什么成功，更难在下一次稳定复现。

困难项目本来就不应该期待一次完成。可以多给 AI 一些机会，也可以允许不同方向的尝试。真正需要关注的是：每一轮是否增加了新的证据，是否缩小了问题范围，是否减少了重复错误，是否把有效经验保存了下来。

只要这些事情在发生，项目就在一步步推进。

最终，我们要建立的不是一个“永远不会犯错的 AI”，而是一套即使 AI 会犯错，也能够发现错误、追溯错误、吸收经验并继续前进的工程协作系统。
