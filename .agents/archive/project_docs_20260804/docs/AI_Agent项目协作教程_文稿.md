# 把 AI Agent 变成可管理的工程团队

副标题：从接手陌生项目，到规则体系、主线—分支协作与低随机性交付  
案例背景：ResNet50 INT8 / NDP 配置、比特流与 RTL 验证项目  
建议时长：35～45 分钟  
建议页数：20 页

---

## 第 1 页｜把 AI Agent 变成可管理的工程团队

### 页面文案

- 从“能回答”走向“能持续交付”
- 项目接手｜规则架构｜主线—分支｜人类干预｜上下文管理

### 讲解词

今天不讨论某个模型的提示词技巧，而是讨论一个更工程化的问题：怎样让 AI Agent 在复杂项目里持续工作，并且让工作可以交接、可以追溯、可以并行、可以被人控制。

核心结论是：Agent 的能力很重要，但决定复杂项目能否长期推进的，往往是它外面的协作系统。我们要把目标、状态、规则、证据和失败经验放进一个可维护的项目结构，而不是只留在某段对话里。

### 项目依据

- `.agents/agent.md`
- `.agents/plan.md`
- `.agents/history.md`

## 第 2 页｜Agent 不是更长的聊天，而是带工具的执行闭环

### 页面文案

**普通会话**

- 以回答当前问题为主
- 状态主要留在聊天记录
- 结果通常需要人再执行

**Agent**

- 围绕目标持续规划
- 能读取项目、调用工具、修改文件、运行验证
- 根据执行结果继续调整

页面底部结论：**会话解决“一次回答”，Agent 负责“一段工作”。**

### 讲解词

Agent 可以理解成“会话能力 + 工具 + 工作区 + 反馈循环”。它不仅给建议，还可以读取仓库、编写代码、运行测试、观察错误，再决定下一步。

因此，相比普通会话，Agent 的优势不是单次回答一定更聪明，而是它能把思考和执行连接起来：提出方案、产生可检查的改动、得到真实反馈、再继续推进。

---

## 第 3 页｜Agent 的优势来自可执行、可验证、可分工

### 页面文案

1. **直接作用于项目**  
   读取代码、生成制品、执行测试，而不是只给操作建议。

2. **用证据闭环**  
   用日志、哈希、测试结果和回读数据判断是否完成。

3. **可以分工协作**  
   主线负责调度，分支负责专项任务，结果再回到主线汇总。

### 讲解词

复杂工程最容易出现“解释听起来正确，但运行不起来”。Agent 的真正价值，是让判断尽量落到项目事实上：源码、配置、真实消费者、测试、服务器返回和最终输出。

它也适合拆分为多个相互隔离的执行面。每条分支只读自己需要的规则和资产，主线负责整体目标与接口，这比让一个无限变长的对话承担全部事情更稳定。

## 第 4 页｜它仍然有四个无法绕过的限制

### 页面文案

- **上下文有限**：项目大于单个对话可完整容纳的范围。
- **压缩会丢细节**：多次压缩后，目标、约束和失败原因可能变模糊。
- **输出有随机性**：同一问题可能得到质量不同的方案。
- **长链任务很脆弱**：复杂任务中一处错误就可能让整条链无法运行。

页面底部结论：**不要把“记住一切、自动纠错、一次成功”当作系统前提。**

### 讲解词

上下文填满后，系统通常会压缩旧内容。压缩不是无损存档：越靠前、越细节化的信息越可能被概括，压缩多次后，Agent 甚至会忘记自己为什么采用当前路线。

随机性在长链任务中会被放大。假设一个流程有十个环节，每个环节都“多数时候正确”，最终一次完整成功的概率仍可能很低。Agent 也不一定会主动发现计划本身代价过大；它经常会沿着既有方向继续尝试，直到明确遇到阻塞。

## 第 5 页｜接手项目的第一步不是修改，而是建立项目地图

### 页面文案

**先回答四个问题**

1. 最终交付目标是什么？
2. 项目有哪些模块，各自负责什么？
3. 已完成、未完成、已冻结的部分分别在哪里？
4. 用什么证据判断“真的完成”？

**第一轮只产出**

- 项目地图
- 核心目标
- 当前状态
- 风险与未知项

### 讲解词

接手陌生项目时，先让 Agent 通读仓库，但要明确它的第一轮任务是“理解并汇报”，不是立刻修复。它需要识别源码、配置、测试、生成产物、历史证据和外部依赖，并给出模块之间的关系。

人要重点检查 Agent 给出的“核心目标”是否准确。目标一旦错了，后续做得越快，偏离越远。对复杂硬件或编译链项目，还要追问：每一层的输出由谁消费，最终成功由什么可观测证据确认。

## 第 6 页｜案例项目把核心目标压缩成一条三方闭环

### 页面文案

**核心目标**

`ONNX / W3 golden ↔ config-bound simulator ↔ stock-RTL hardware`

**项目规模**

- 78 个 ONNX 节点
- 133 个 typed hardware stage
- 10 类硬件 stage family

页面底部结论：**“JSON 合法”不等于“硬件正确”；三方输出一致才算闭环。**

### 讲解词

ResNet50 INT8 项目最初容易被理解成“把 ONNX 转成算子 JSON”。但真正目标不是文件生成，而是同一冻结输入在软件公式、配置绑定模拟器和 stock RTL 硬件上得到一致结果。

这条目标把大量局部任务放回同一坐标系：JSON、mapping、bitstream、execplan、SCA、physical readback 都只是中间层。任何一层通过，都不能替代最终三方闭环。

### 项目依据

- `.agents/plan.md` 的“核心目标与三方口径”
- `contracts/resnet50_r5_lowering_bundle.json`
- `contracts/resnet50_project_closure.json`

## 第 7 页｜规则文件要形成分层架构，而不是一份无限增长的说明书

### 页面文案

```text
根规则入口：AGENT(S).md
├─ 当前状态与短期计划：plan.md
├─ 历史与任务记录：history.md / task_records/
├─ 公共规则：rules/生成前必读索引、通用生成与测试规则
├─ 分支专项规则：rules/<算子族或任务>.md
└─ 关键决策：decisions/ADR-*.md
```

页面底部结论：**稳定信息向上放，易变化信息向下拆，历史信息移出活动上下文。**

### 讲解词

根规则文件是每个新任务的稳定入口。不同工具可能使用 `AGENTS.md`、`AGENT.md` 或项目自定义路径；本项目实际使用 `.agents/agent.md`。名字不是重点，职责才是重点。

根规则不能变成所有信息的堆积区。它只需要告诉 Agent：项目目标、稳定边界、各类信息去哪里读、事实冲突时谁优先、协作方式和不可越过的权限边界。

### 项目依据

- `.agents/agent.md`
- `.agents/rules/`
- `.agents/decisions/`
- `.agents/task_records/`

---

## 第 8 页｜根规则文件只保留每个任务都必须知道的内容

### 页面文案

**应该包含**

- 项目核心目标与完成口径
- 模块、资产和规则索引
- 事实优先级与权限边界
- 主线—分支协作方式
- 全局工作纪律

**不应该包含**

- 某一版本的长日志
- 已结束任务的逐步过程
- 临时命令和短期 blocker
- 某个分支才需要的字段细节

### 讲解词

根规则文件最大的风险是越写越长。它一旦太长，每个任务都会为无关信息付出上下文成本，也会增加规则之间互相冲突的概率。

本项目的稳定入口明确规定：当前任务只看 `plan.md`，生成规则去 `rules/`，完成证据去 `task_records/`，旧版本和被取代结论去 `history/` 与 `archive/`。这种“唯一归属”让 Agent 不需要在多个文件里猜哪一份才是当前口径。

### 项目依据

- `.agents/agent.md` 的“文档唯一归属”
- `.agents/history.md` 的“活动 agent/plan 精简”

---

## 第 9 页｜计划、历史、分支规则各自只承担一种时间尺度

### 页面文案

**Plan：现在与下一步**

- 当前状态
- 短期任务
- blocker、顺序、停止门

**History / Task Record：已经发生**

- 做过什么
- 成功或失败的证据
- 错误如何定位

**Branch Rule：以后怎么做**

- 专项语义
- 已知反例
- 必须检查的门
- 允许与禁止的操作

### 讲解词

这三个文件类型分别对应现在、过去和未来。计划文件不应该保存完整历史；历史文件不应该继续使用“下一步”这种易过期措辞；规则文件不应该记录某个临时包的 SHA 或某一次日志行号。

一次任务结束后，要把过程从活动计划中移走：事实写入 task record，可推广经验写入规则，只属于某个版本的细节进入历史。这样 Agent 每次重读的是已经提纯的信息，而不是重复吞下所有聊天与日志。

### 项目依据

- `.agents/agent.md`
- `.agents/history.md`
- `.agents/task_records/`
- `.agents/rules/`

## 第 10 页｜这套文件体系解决三类长期问题

### 页面文案

1. **交接不依赖账号或对话**  
   新 Agent 读取仓库即可恢复工作；再用 GitHub 做异地备份。

2. **上下文按需加载**  
   压缩后重读稳定入口；分支只读相关规则，减少污染与性能损失。

3. **经验逐步固化**  
   成功与失败都提炼为规则、测试或校验门，降低重复犯错概率。

### 讲解词

第一，项目知识从某个账号、某段聊天迁移到仓库。即使任务、设备或账号发生变化，也不会丢失全部进度。规则和证据最好进入 Git，并有远端备份，防止误删和本地损坏。

第二，上下文变成“按需装载”。压缩后不要求 Agent 回忆全部对话，而是重新读取短小稳定的入口；分支只读与自己最终消费字段相关的文件。

第三，随机试错被转化为工程资产。错误如果只留在聊天里，下次还会再犯；如果被提炼成规则、反例和自动检查，它就变成系统能力的一部分。

### 项目依据

- `.agents/history.md`：活动文档压缩与快照
- `.agents/rules/生成前必读索引.md`
- Git 历史与远端备份策略

## 第 11 页｜主线是控制面，分支是执行面

### 页面文案

**主线**

- 与人交互、维护总目标
- 修改 plan 与公共规则
- 冻结任务单并分发
- 汇总 blocker、证据和整网进度

**分支**

- 只处理一个算子族或明确专项
- 维护本族生成器、validator、配置和证据
- 遇到阻塞回传主线
- 不直接修改公共计划和规则

**条件分支**

- 只有跨算子的 runner / observer / 封包问题出现时，才启用公共基础设施线

### 讲解词

主线不做普通执行任务，是一个非常重要的设计。它保持低负载，随时可以回答人的问题、调整优先级、处理跨分支冲突、冻结新的任务单。

分支完成纵向闭环，但不能自己修改全局口径。它向主线提交结构化结果，例如 `RETURN_ANALYSIS`、`RULE_DELTA_PROPOSAL`、`BLOCKER_DELTA` 和新的 `PACKAGE_RELEASE`。公共规则是否修改，由主线根据证据裁决。

### 项目依据

- `.agents/agent.md` 的“三级协作架构”

---

## 第 12 页｜并行提高速度，但不会凭空增加总能力

### 页面文案

**收益**

- 多个独立任务同时推进
- 每个分支上下文更纯净
- 主线始终可用于项目交互

**代价**

- 任务分发、回传、规则同步有通信成本
- 共享资源仍有物理上限
- 错误拆分会制造重复工作

**案例**

- 6 条执行线
- 3 个独立服务器根
- 同一根目录同一时刻只运行 1 个包

### 讲解词

并行主要减少等待时间，不代表同样的算力突然能完成更多总工作。任务拆分、上下文准备、结果合并都会带来额外开销，所以只对依赖清晰、资产隔离、验收明确的任务并行。

本项目采用六条执行线和三个服务器根，两个执行线共享一个根做双缓冲。服务器运行的物理并行度最多为三，而且同一根目录必须独占。主线还要根据资源争用主动降低并行度，而不是牺牲证据身份。

### 项目依据

- `.agents/agent.md` 的“六条执行线与三服务器双缓冲流水”

---

## 第 13 页｜上下文管理的关键是“路由”，不是“把所有内容塞进去”

### 页面文案

**任务开始**

- 读稳定入口
- 根据本轮动作选择公共规则与专项规则
- 记录路径、SHA、读取原因

**执行中**

- 只保留当前目标、冻结输入、决策与最新证据
- 不混入其他算子族的细节

**压缩后**

- 重读入口、计划相关段落和专项规则
- 从 task record 恢复必要事实，不重放全部历史

### 讲解词

上下文管理不是简单删字，而是建立信息路由。这个项目的“生成前必读索引”会根据动作类型决定本轮必须读哪些文件、哪些文件只在条件满足时读取。

读取收据还会记录规则文件的 SHA。这样当规则发生变化时，可以判断某个候选是否仍符合当前口径。它同时避免另一种浪费：为了保险让每个分支把所有规则都读一遍，最终反而把重要信息淹没。

### 项目依据

- `.agents/rules/生成前必读索引.md`

## 第 14 页｜先计划后执行，把“理解偏差”暴露在低成本阶段

### 页面文案

**任务单至少冻结**

- 目标与完成口径
- 输入、版本和规则 SHA
- 允许写入的路径
- 失败分流与停止条件
- 测试预算和外部操作权限

**执行前必须做**

1. Agent 复述计划与假设
2. 不懂的地方先提问
3. 人确认路线后再修改与运行

### 讲解词

AI 不一定真正理解你想要什么。先要求它给出计划，或者把人的计划交给它复述，可以在最便宜的阶段发现误解。

任务单还要明确“失败后去哪一条路”。是配置语义错误、RTL 错误、observer 错误，还是封包基础设施错误？如果不提前定义，分支容易在遇到失败后自行扩大范围，反复试不同改动，最终无法判断哪一步产生了效果。

### 项目依据

- `.agents/agent.md` 的“标准派发与回传”
- `.agents/plan.md` 的执行门和运行队列

## 第 15 页｜人类最重要的作用，是在长期阻塞时改变问题

### 页面文案

**观察四个信号**

- 多轮尝试没有新增证据
- 代价持续上升，验证范围却没有收窄
- Agent 只是在同一路线更换实现细节
- 测试不能区分候选原因

**人类干预动作**

- 重新定义问题边界
- 补充缺失的系统知识
- 改变验证顺序或观测点
- 暂停分支，换方向或换模型

### 讲解词

分支通常不会自动判断“这个计划整体不合理”。只要还有可尝试的动作，它可能继续沿着原路线推进；如果卡住，也可能只报告当前 blocker，而不重新定义问题。

人的价值不只是批准按钮，而是判断方向。尤其当多轮迭代没有产生新的区分性证据时，要主动问：是不是缺少某个消费链知识？是不是测试看错了层？是不是应该从输出倒推，而不是继续微调输入？

## 第 16 页｜案例：直接模仿算子 JSON，迭代多次仍不收敛

### 页面文案

**最初路线**

`ONNX → 计算步骤 → 参考 JSON → 仿写新 JSON → 上机测试`

**为什么效果差**

- JSON 字段不是纯粹的数学表达
- 字段绑定硬件单元、地址生命周期和控制时序
- “格式相似”不能证明“消费者语义相同”
- 服务器失败只能说明链路某处错误，无法直接定位字段

### 讲解词

项目初期曾尝试让 Agent 从 ONNX 和已有 JSON 学会直接写新算子配置。这个思路看起来合理，但多轮迭代效果不佳，因为参考 JSON 只是硬件行为的一个表面投影。

Agent 知道算子公式，不代表它知道每个 JSON 字段如何被 encoder、planner 和 RTL 消费。只模仿文件结构，容易得到“能解析、能编码、甚至能启动，但数值或时序不正确”的配置。

## 第 17 页｜转折点：把 JSON 后面的消费链完整交给 Agent

### 页面文案

**补齐四层知识**

1. 已有算子 JSON 对应的真实计算步骤
2. JSON 如何被 mapper / encoder 消费并生成 bitstream
3. bitstream、execplan、SCA 如何驱动运行
4. RTL 中字段对应的单元、握手、地址与完成条件

页面底部结论：**不是给更多文字，而是补齐“输入如何变成硬件行为”的因果链。**

### 讲解词

人的干预不是继续强调“请认真一点”，而是补齐了 Agent 原来无法推断的系统知识：参考算子在硬件上到底做了什么、配置如何进入比特流、比特流如何被 RTL 执行，以及最终数据如何回读。

这些知识随后被写进公共规则、硬件字段语义、算子专项规则和 validator。Agent 不再只根据“长得像”生成 JSON，而是能够沿着计算、编码、地址、生命周期和 RTL 消费者逐层验证。

### 项目依据

- `.agents/rules/算子配置规则.md`

## 第 19 页｜减少随机性：硬约束强于规则，规则强于口头提醒

### 页面文案

**约束强度**

`代码硬约束  >  规则文件约束  >  用户口头约束`

**把经验升级为门**

- 生成前必须有规则读取收据
- 规则或输入身份变化，旧候选自动失效
- 最终包必须通过 current-rule 独立自检
- 缺证据、身份不一致或字段未知时 fail closed

### 讲解词

口头约束最容易在几次压缩后消失。规则文件更稳定，但 Agent 仍可能漏读、误读或不严格执行。最可靠的做法，是把关键要求同时写进规则和代码校验。

例如，生成测试包前必须通读对应规则并记录 SHA；包生成完成后，还要对最终 ZIP 和 sidecar 重新执行 current-rule 自检。如果规则在生成后发生变化，旧自检失效，候选必须隔离或重新构建。这样“记得遵守”被升级为“违反就无法通过”。

## 第 20 页｜一套可直接复用的项目操作法

### 页面文案

1. **先画地图**：通读项目，冻结核心目标与完成证据。
2. **再建规则**：根入口、短计划、历史台账、分支专项各司其职。
3. **主线调度**：主线保持可交互，分支独立执行并结构化回传。
4. **先计划再动手**：把假设、权限、停止门和失败分流写清楚。
5. **把经验变成门**：成功与失败都沉淀为规则、反例和自动校验。

页面底部结论：**AI 会犯错，但只要每一轮都增加可复用证据，系统就会越来越稳。**

### 讲解词

如果效果不理想，不要急着得出“AI 不适合复杂项目”的结论。先检查协作方式：目标是否足够明确，Agent 是否看到了真实消费链，任务是否被合理拆分，是否有区分性测试，关键规则是否已经代码化。

困难项目本来就不应期待一次完成。可以让不同分支从不同方向尝试，也可以更换模型或 Agent。但这些尝试必须回到同一套证据和规则体系里。只要问题边界在收窄、可复用知识在增加、重复错误在减少，项目就在真正推进。
