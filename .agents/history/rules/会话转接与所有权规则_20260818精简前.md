# 会话转接、所有权与整批换代规则

最后更新：2026-08-11（建立唯一 owner registry、无重叠切权和主线优先换代）

本规则适用于主线、算子族、人工 JSON、公共基础设施和专项 owner 的 Codex 会话替换。它只
转移既有职责和状态，不扩大新会话权限，不授权 package/server/RTL/config/numeric 外部动作。

## 1. 稳定角色与唯一活动会话

规则 ID：`CDA-SESSION-STABLE-ROLE-UNIQUE-ACTIVE-OWNER-001`

职责必须绑定稳定 `role_id`，不能把 thread/task ID 当作长期角色身份。活动映射唯一来自
`contracts/current_session_owner_registry_v1.json`，schema 为
`session-owner-registry-v1`。registry 必须满足：

1. 恰好一个 `MAINLINE` role，且 `mainline_role_id`精确指向它；
2. 每个 role 恰好一个 `ACTIVE` thread，同一 thread 不得占有两个 role；
3. 每次切权只增加一个 role 的 `owner_epoch`，registry `registry_epoch`也只加一；
4. 每个 role 记录 scope、write/forbidden scope、current task、latest task record 和 in-flight
   package/return/server lease；没有外部状态时必须显式 `NONE`，不能留空猜测；
5. registry 绑定 `.agents/agent.md`、current plan、本规则和生成索引的 exact receipts。

`.agents/plan.md`、历史 task record、工具源码中的 thread ID 都不是 current owner pointer。
历史 ID 保留 provenance，不批量重写；任何新派发、完成通知和 return 路由必须在动作时读取
current registry 和 epoch。

## 2. 四阶段无重叠切权

规则 ID：`CDA-SESSION-PREPARE-ACCEPT-ACTIVATE-RETIRE-001`

每个 role 严格按下列状态机转接：

```text
OLD_ACTIVE
  → HANDOFF_PREPARED（旧 owner 仍唯一写者）
  → NEW_ACCEPTED_READ_ONLY（新会话只读核验）
  → REGISTRY_ACTIVATED（单 role、单 epoch 原子切换）
  → OLD_RETIRED_READ_ONLY / NEW_ACTIVE
```

- `HANDOFF_PREPARED`前旧 owner 生成机器 capsule；旧 owner 在 activation 前仍承担现有职责，
  但不得在 capsule 后静默改变已绑定任务/资产。发生变化必须废弃 capsule 并重建。
- 新会话在 activation 前只能读取和生成 acceptance，不得改公共/本族资产、发包、运行服务器、
  取 lease、发送正式 owner 结论或接管外部状态。
- 只有 acceptance 对 capsule、registry 和全部收据逐字节一致且 conflicts=`[]`时才允许 activation。
- activation 必须先生成独立 successor registry并验证“只改一个 role”；再由
  `tools/session_handoff.py publish-activation`按 expected-old-SHA 原子替换正式 registry。
  current registry已漂移时陈旧activation必须fail closed。发布后旧 owner立即变为
  `RETIRED_READ_ONLY`，不能再补写。
- UI 中 archive/关闭旧会话是 activation 后的清理动作，不得先关旧会话再寻找状态。

禁止两个会话用“协作”“临时并行”名义同时写同一 role scope。需要并行必须新增不同 stable
role 和互斥 write scope，而不是共享 owner。

## 3. Handoff capsule 最小完备集

规则 ID：`CDA-SESSION-HANDOFF-CAPSULE-COMPLETE-STATE-001`

每份 `session-handoff-capsule-v1` 至少绑定：

- role kind/scope、old/new thread ID、registry/owner epoch、current mainline thread；
- `.agents/agent.md`、current `.agents/plan.md`、生成索引、本规则，以及该 role 所有专项规则的
  path/bytes/SHA读取收据；
- 当前 objective/status/next action、open/closed blocker、claim boundary；
- latest task record、current-family/current-adjudication pointer、实际使用的 generator/validator；
- pending/current package和return的path/bytes/SHA、唯一命令、服务器根和lease状态；
- dirty worktree 中本 role 已授权未提交路径，以及不得触碰的foreign paths；
- 尚未发送/消费的用户消息、主线裁决、RULE_DELTA/CONFIRMATION和第一项恢复动作。

状态为`SERVER_RUNNING`时不得省略server root、lease和exact package；状态为
`RETURN_COLLECTED/ANALYZING`时不得省略return receipt。转接不改变package identity、lease owner、
formal result或server state；新 owner只继承记录的授权边界。

## 4. 主线替换顺序

规则 ID：`CDA-SESSION-MAINLINE-FIRST-CAMPAIGN-001`

整批换代必须先换主线，再逐 role 换 owner：

1. 旧主线暂停新派发及 plan/public-rule 写入，先生成并验证完整 current registry；
2. 创建新主线，新主线以`ACCEPTED_READ_ONLY`读取稳定入口、current plan、生成索引、本规则、
   current-family pointers、package storage index、全部 in-flight 状态和最近全局 task record；
3. 只对 mainline role 原子 activation，旧主线立即退休；
4. 从此所有旧/新 owner 的通知都动态解析到新主线；旧派发单中的旧主线 ID只作 provenance；
5. 新主线再对其它 role逐个或并行准备 capsule，但每个 role单独 acceptance/activation；
6. campaign 最终检查：除显式排除 thread外，before registry的每个 role都恰好切换一次，role
   exact-set不变、owner epoch各加一、activation order连续且 mainline=`1`。

本次用户计划固定排除本专项会话
`019fd276-14c5-7800-94db-87ebfb9ce632`；若它在 registry 中拥有 role，campaign 前后该 role
必须逐字段不变。排除不等于它成为主线、代替其它 owner或接收无关进度广播。

## 5. 动态主线路由与迟到结果

规则 ID：`CDA-SESSION-CURRENT-MAINLINE-RESOLUTION-NOT-HARDCODED-001`

package/return完成通知发送前必须执行
`tools/session_handoff.py resolve-mainline`或等价 registry解析，并同时携带：

- `dispatched_mainline_thread_id`（历史派发 provenance）；
- `resolved_mainline_thread_id`和`registry_epoch_at_send`（当前正式目标）；
- owner `role_id/thread_id/owner_epoch`。

若派发后主线已替换，结果发送到 resolved current mainline；不得因旧 task record/脚本硬编码而
发回退休主线。若 owner 自身已替换，旧 owner收到迟到用户消息或 return时只能把原始消息交给
current owner，不得继续分析或写资产。无法读取/验证 registry 时停止正式回传并报告
`SESSION_OWNER_POINTER_UNAVAILABLE`，不能猜 ID。

## 6. In-flight package、服务器与外部状态

规则 ID：`CDA-SESSION-HANDOFF-EXTERNAL-STATE-NONMUTATING-001`

- `PACKAGE_READY_NOT_RUN`可转接，但 package/sidecar/final audit/storage pointer必须冻结；新 owner
  不重建、不改名，除非另有规则/身份变化要求 fresh successor。
- `SERVER_RUNNING`可在不触碰服务器的情况下转移监护责任；capsule必须保留root/lease/package/
  expected return，旧 owner activation 后不得再发服务器命令。
- `RETURN_COLLECTED/ANALYZING`可转接 exact return和已完成分析收据；禁止两边重复解析后各自写
  不同裁决。
- handoff自身不得上传、运行、停止server、取/释放lease、修改package或删除旧结果。

## 7. 机器工具、阻断门和负控

共享资产：

- `schemas/session_owner_registry_v1.schema.json`
- `schemas/session_handoff_capsule_v1.schema.json`
- `schemas/session_handoff_acceptance_v1.schema.json`
- `schemas/session_handoff_activation_v1.schema.json`
- `schemas/session_handoff_publication_v1.schema.json`
- `tools/session_handoff.py`
- `tests/test_session_handoff.py`

阻断只映射到 ownership/authorized write/return routing/external-state continuity。以下必须fail closed：

1. duplicate active thread/role或零/多主线；
2. new thread等于old thread、已拥有其它role或被campaign明确排除；
3. required read/task/package/return/rule receipt漂移；
4. acceptance与capsule/new thread不一致，或新会话在acceptance前声称已写入/执行外部动作；
5. activation同时改变两个role、epoch跳变、old owner未退休或new owner未ACTIVE；
6. 整批换代漏role、重复role、先换family后换mainline，或改变excluded role；
7. 完成通知仍只使用旧硬编码主线ID。

描述性标题、UI排序、是否立即archive旧会话只作`record_only`；不得因这些展示项阻断实际任务。

## 8. 完成口径

单 role只有同时存在 capsule、`ACCEPTED_READ_ONLY`、successor registry、activation receipt和
`REGISTRY_ACTIVATED` publication receipt才算
转接完成。整批换代只有 campaign audit PASS、所有新 owner已向current mainline发送一条
`HANDOFF_ACTIVATED`收据、所有旧 owner已停止写入，才可恢复常态派发。转接完成不改变任何算子
E级、package release、natural terminal、正式D、E4/E5或RTL/config裁决。
